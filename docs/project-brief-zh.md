# MiniCloudKV：書審專案摘要（截至 2026-09-25）

本專案以三節點 Key-Value Store 探索「節點會當機、網路會分區時，一筆寫入何時能被安全地回覆成功」。專案使用 Python 標準函式庫實作 Raft 的任期與投票持久化、依照日誌新舊程度投票、領導者選舉、日誌複寫、衝突後綴修復與多數節點提交。每個節點將任期、投票、日誌和提交位置以附帶 CRC32 檢查的追加式 WAL 及定期原子快照儲存；重啟時只重播已提交的操作。為避免分區期間讀到舊資料，讀取也必須提交一筆非修改性的日誌紀錄。

驗證使用三個真實 HTTP 行程：寫入成功後殺掉領導者，確認新領導者仍能讀出資料，並確認舊節點重啟後追上；另以雙向阻斷 RPC 隔離原領導者，驗證它不能確認缺乏多數同意的寫入。另附小型線性一致性檢查器，對單一鍵、至多 16 筆已成功完成的操作，搜尋是否存在符合實際先後順序的序列執行。

目前十六項自動測試通過，新增併發請求逾時、慢節點投票、日誌追趕與快照後 WAL 清理測試。一次本機 WAL 模式實測中，殺掉領導者到新領導者首次成功讀取既有值約 460.6 毫秒。修正後各進行三次 1,000 筆循序 PUT 的對照測試，完整狀態重寫與 WAL 的吞吐量中位數分別為 179.34 與 321.68 ops/s；這是特定容器與短工作負載下的結果，不能推論到所有場景。

實驗過程中，初版 WAL 因每次複製整份日誌，效能反而比完整狀態重寫慢；改以只複製日誌索引串列後，才在上述測試中取得改善。目前每筆操作仍需另外同步記錄提交位置，而且快照保留完整日誌，尚未做日誌壓縮。下一步會測量超過快照週期的長工作負載，分析 fsync、序列化及尾端延遲，再研究安全的 InstallSnapshot、日誌壓縮與 group commit。專案程式、可重現指令、測試及限制均在倉庫中。
